## 项目背景与目标

### 当前状态

Nexlyn 平台已通过 `pkg/skylarkq` 引擎实现了 Skylark 事件数据的查询能力，包括：

- ✅ **事件列表查询**：支持关键词搜索、组织过滤、分页
- ✅ **事件详情查看**：完整的流转历史、处理人信息
- ✅ **统计分析**：时长统计、状态统计、趋势分析、节点统计等 7 种分析维度
- ✅ **权限过滤**：基于组织映射表实现的权限隔离

**技术实现方式**：直连 Skylark 平台的 PostgreSQL 映射数据库

### 项目目标

**核心需求**：避免用户频繁在 Nexlyn 和 Skylark 两个平台之间切换

**期望实现的能力**：
1. **任务处理**：查看我的待办、处理任务（通过/拒绝/转发）
2. **消息推送**：流程状态变更时自动推送微信消息

**用户场景**：
- **电脑端**：在 Nexlyn 平台完成所有事件管理和流程处理操作
- **手机端**：通过微信服务号接收推送、快速处理待办任务

## 当前能力与需求缺口

### 已实现能力（只读查询）

| 功能模块 | 实现状态 | 说明 |
|---------|---------|------|
| 事件数据查询 | ✅ 已完成 | 查询远程数据库，支持复杂筛选 |
| 组织权限过滤 | ✅ 已完成 | 基于组织映射表实现 |
| 事件详情查看 | ✅ 已完成 | 完整流转历史和处理人信息 |
| 统计分析 | ✅ 已完成 | 7 种统计维度 |

### 需要新增能力（写操作）

| 功能模块 | 实现难度 | 依赖条件 |
|---------|---------|---------|
| 任务处理操作 | 中 | 用户身份映射机制 |
| 我的待办列表 | 低 | 基于现有查询能力 |
| 微信消息推送 | 高 | 微信服务号开发或使用 Skylark 已有服务号 |

### 核心挑战

**身份映射问题**：
- Nexlyn 和 Skylark 是两套独立的用户体系
- 需要建立用户和组织的对应关系
- 流程操作时需要明确"代表哪个 Skylark 用户"执行

**数据一致性问题**：
- 如果同步用户/组织数据，如何保证两边数据一致？
- 如果不同步，如何实现权限控制？

**微信推送问题**：
- 使用 Skylark 的微信服务号还是 Nexlyn 自己的？
- 手机端用户体验如何设计？

### 工作流程

#### 1. 用户和组织同步

**初始化同步**：
1. 管理员在 Nexlyn 创建租户、组织架构、用户账号
2. 系统自动调用 Skylark API 在对方平台创建对应的用户和组织
3. 系统维护 ID 映射表（Nexlyn user_id ↔ Skylark user_id）

**日常同步**：
- Nexlyn 创建新用户 → 自动同步到 Skylark
- Nexlyn 调整组织架构 → 自动同步到 Skylark
- Nexlyn 修改用户信息 → 自动同步到 Skylark

**同步实现方式**：
- 使用数据库事务保证两边操作的原子性
- Nexlyn 数据库写入成功 + Skylark API 调用成功 → 整体成功
- 任何一步失败 → 事务回滚，操作失败

**ID 映射表结构示例**：
```
nexlyn_user_id    →  skylark_user_id
user-001          →  skylark_123
user-002          →  skylark_456

nexlyn_org_id     →  skylark_org_id
org-hq            →  skylark_org_789
org-branch-1      →  skylark_org_790
```

#### 2. 流程操作

**发起流程**：
1. 用户在 Nexlyn 填写表单，点击"提交"
2. Nexlyn 通过 ID 映射表查询该用户对应的 Skylark user_id
3. 调用 Skylark API 创建流程实例（携带 Skylark user_id）
4. 返回流程实例 ID，记录在 Nexlyn 系统

**处理任务**：
1. 用户在 Nexlyn 查看待办列表
2. 点击"通过/拒绝"按钮
3. Nexlyn 通过 ID 映射表查询该用户的 Skylark user_id
4. 调用 Skylark API 提交处理结果
5. 更新 Nexlyn 界面显示最新状态

#### 3. 微信推送（使用 Skylark 服务号）

**电脑端操作**：
- 用户在 Nexlyn 网页端完成所有流程操作
- 界面统一、体验流畅

**手机端操作**：
- Skylark 流程状态变更 → 自动推送微信消息
- 用户在微信中点击消息 → 进入 Skylark 服务号处理页面
- 在 Skylark 服务号内完成流程审批、评论等操作

**优势**：
- 利用 Skylark 已有的微信服务号基础设施
- 无需 Nexlyn 单独开发微信公众号
- 推送功能开箱即用

### 主要优势

#### 1. 技术实现简单
- **无需自建微信服务号**：直接使用 Skylark 的微信推送能力
- **API 调用直接**：每个操作都是单次 API 调用，无需复杂的代理逻辑
- **开发周期短**：预计 3-4 周完成核心功能

#### 2. 用户体验自然
- **身份统一**：Skylark 侧有真实的用户账号，流程历史记录完整
- **权限清晰**：Skylark 的权限体系完整工作
- **微信推送成熟**：Skylark 的微信推送功能已验证稳定

#### 3. 性能和可靠性
- **无批量操作**：每次用户操作都是单次同步，不存在大批量失败风险
- **事务保证**：通过数据库事务保证两边数据一致性
- **失败即回滚**：任何一步失败都会回滚，不会出现半成功状态

### 核心风险

#### 🔴 风险 1：管理员误操作导致数据不一致

**问题描述**：
- Skylark 平台的管理员可能手动修改同步过来的用户或组织
- 例如：删除用户、移动用户到其他组织、修改用户权限

**影响范围**：
- Nexlyn 的组织映射表失效（组织 ID 对应关系错误）
- 事件查询权限混乱（用户看到不该看的数据或看不到应该看的数据）
- 流程操作失败（用户 ID 不存在或无权限）

**缓解措施**：
- 与 Skylark 官方沟通，确认能否**限制管理员权限**（不允许修改同步过来的用户/组织）
- 如无法限制，需建立**监控和告警机制**，定期检测数据一致性
- 提供**数据修复工具**，管理员发现不一致时可手动触发重新同步

**发生概率**：中等（取决于对方管理员的操作习惯）

---

#### 🔴 风险 2：用户在微信服务号修改个人信息

**问题描述**：
- 用户可能在 Skylark 微信服务号中修改自己的姓名、手机号、所属组织等信息
- Nexlyn 无法感知这些变更

**影响范围**：
- 两边用户信息不一致
- Nexlyn 显示的用户信息过时

**缓解措施**：
- **关键核实**：向 Skylark 确认能否**关闭微信服务号的用户信息编辑功能**
- 如果无法关闭，需要 Skylark 提供 **webhook 通知**，用户修改信息时通知 Nexlyn
- Nexlyn 收到通知后自动更新本地数据

**发生概率**：低（大部分企业微信应用会关闭此功能）

---

#### 🔴 风险 3：Skylark 无法删除用户

**问题描述**：
- Nexlyn 删除用户（员工离职）后，需要同步删除 Skylark 的用户
- 但 Skylark API 文档未明确提供删除用户接口

**影响范围**：
- 离职员工在 Skylark 仍然存在
- 可能仍会收到微信推送
- 可能仍能通过 Skylark 服务号查看数据

**缓解措施**：
- **关键核实**：向 Skylark 确认是否有**删除用户 API**
- 如果没有删除 API，确认是否有**禁用用户 API**（禁用后用户无法登录和操作）
- 如果都没有，需要在 Skylark 侧手动处理离职员工

**发生概率**：高（员工离职是常见场景）

---

#### 🟡 风险 4：整合前的历史数据难以处理

**问题描述**：
- 两个平台在整合前各自已有大量历史数据
- Nexlyn 平台已有的用户和组织数据
- Skylark 平台已有的流程和事件数据
- 同步功能只对新建数据生效（建立映射关系），历史数据无法自动映射

**影响范围**：
- Nexlyn 的历史用户无法与 Skylark 的历史流程关联
- Skylark 的历史流程数据无法在 Nexlyn 查询（缺少组织映射）
- 需要大量人工工作建立历史数据的映射关系

**缓解措施**：
- **清理历史数据**：如果历史数据不重要，可以考虑清空后重新开始
- **手动建立映射**：提供管理工具，让管理员手动将历史用户与 Skylark 用户关联
- **数据迁移脚本**：开发批量数据迁移脚本，根据姓名、手机号等信息自动匹配
- **分阶段处理**：先处理近期数据，旧数据可以保留在原系统查询

**发生概率**：高（如果两个平台都有历史数据）

---

#### 🟡 风险 5：同步冲突无法自动解决

**问题描述**：
- Nexlyn 和 Skylark 同时对同一数据进行修改
- 例如：Nexlyn 删除用户的同时，Skylark 管理员修改了该用户的组织

**影响范围**：
- 数据冲突，无法确定哪个操作应该生效

**缓解措施**：
- **Nexlyn 为唯一数据源**，所有修改必须从 Nexlyn 发起
- 向 Skylark 确认能否**限制管理员权限**，不允许直接修改同步数据
- 如无法限制，只能通过**定期对账+人工处理**

**发生概率**：低（如果严格规范操作流程）

---

### 向 Skylark 官方核实的问题

#### 关于用户和组织管理
1. ❓ **用户删除**：是否有删除用户的 API？如果没有，是否有禁用用户的 API？
2. ❓ **管理员权限边界**：能否限制 Skylark 管理员不允许手动修改同步过来的用户和组织？
3. ❓ **微信服务号功能开关**：能否关闭微信服务号中用户自助修改个人信息的功能？

#### 关于同步机制
4. ❓ **外部 ID 支持**：创建用户时能否传入外部系统的 ID（如 `external_id: "nexlyn_user_001"`），方便后续查询和映射？
5. ❓ **批量操作**：是否有批量创建/更新用户的 API？（优化首次同步性能）

#### 关于微信推送
6. ❓ **推送跳转**：微信推送消息能否跳转到外部链接（Nexlyn 平台）而不是 Skylark 服务号？
7. ❓ **推送触发条件**：有哪些事件会触发微信推送？（流程发起、待办、超时等）

### 工作流程

#### 1. 用户和组织管理

**数据存储**：
- 所有用户和组织数据只存储在 Nexlyn 平台
- Skylark 侧只有 1 个超级管理员账号
- 不进行用户和组织的同步

**权限控制**：
- 在 Nexlyn 侧完全控制用户权限
- 通过组织映射表实现权限过滤（已有能力）
- Skylark 侧不需要感知具体用户和组织

#### 2. 流程操作（代理模式）

**关键机制**：在流程的每个节点增加"处理人信息"字段，由 Nexlyn 管理

**发起流程**：
1. 用户在 Nexlyn 填写表单，点击"提交"
2. Nexlyn 使用**超级管理员身份**调用 Skylark API
3. 在表单字段中增加隐藏字段：
   - `nexlyn_user_id`：发起人的 Nexlyn 用户 ID
   - `nexlyn_user_name`：发起人姓名
   - `nexlyn_org_id`：发起人所属组织 ID
4. Skylark 创建流程实例，这些字段作为业务数据存储

**处理任务**：
1. 用户在 Nexlyn 查看待办列表（通过组织映射查询）
2. 点击"通过/拒绝"按钮
3. Nexlyn 使用**超级管理员身份**调用 Skylark API
4. 同时传递当前处理人的 Nexlyn 信息：
   - `nexlyn_handler_id`：处理人的 Nexlyn 用户 ID
   - `nexlyn_handler_name`：处理人姓名
5. Skylark 记录处理结果，包含 Nexlyn 的处理人信息

**流程节点配置**：
- 在 Skylark 配置流程时，每个节点不设置"处理人范围"限制
- 所有节点对超级管理员全部开放
- 实际的权限控制由 Nexlyn 实现

#### 3. 微信推送（Nexlyn 自建服务号）

**流程状态同步**：
- Skylark 流程状态变更时，通过 **webhook** 通知 Nexlyn
- Nexlyn 接收通知，解析流程状态
- 根据处理人的 Nexlyn 用户 ID，查询该用户的微信 openid

**消息推送**：
- Nexlyn 调用微信模板消息 API，推送待办通知
- 用户在微信中点击消息 → 跳转到 Nexlyn H5 页面
- 在 Nexlyn H5 页面完成流程审批操作

**优势**：
- 品牌统一：使用 Nexlyn 自己的微信服务号
- 体验统一：电脑端和手机端都是 Nexlyn 平台
- 完全自主：消息模板、跳转链接完全可控

### 主要优势

#### 1. 数据一致性有保障
- **Nexlyn 是唯一数据源**：不存在双向同步冲突
- **不受对方平台影响**：Skylark 管理员无法误操作用户/组织
- **组织架构调整灵活**：Nexlyn 调整组织架构不影响 Skylark 侧

#### 2. 权限控制完全自主
- **Nexlyn 完全控制权限**：谁能查看什么数据、谁能处理什么任务
- **组织映射表永远准确**：不会因同步问题导致映射失效
- **权限调整实时生效**：无需等待同步

#### 3. 品牌和体验统一
- **电脑端**：Nexlyn 平台
- **手机端**：Nexlyn 微信服务号
- **推送消息**：Nexlyn 品牌
- **用户认知**：只需要记住 Nexlyn 一个平台

#### 4. 扩展性强
- **多平台接入**：未来可以接入其他流程引擎（不只是 Skylark）
- **统一身份体系**：可以实现单点登录（SSO）
- **灵活集成**：可以集成 Nexlyn 其他模块的微信推送

### 核心挑战

#### 🟡 挑战 1：微信服务号开发

**工作内容**：
- 申请微信服务号（企业主体）
- 开发微信推送功能（模板消息、JSAPI 签名）
- 开发 H5 流程处理页面（适配微信内置浏览器）
- 维护微信 token 刷新机制

**开发周期**：预计 3-4 周

**优势**：
- 完全自主可控
- 可以集成 Nexlyn 其他模块的推送（IoT 告警、视频事件等）
- 品牌统一

### 向 Skylark 官方核实的问题

#### 关于流程操作能力
1. ❓ **业务字段扩展**：能否在流程表单中增加自定义业务字段（如 `nexlyn_user_id`、`nexlyn_user_name`、`nexlyn_org_id`）用于记录实际操作人和权限过滤？
2. ❓ **流程节点配置**：能否在配置流程时，通过业务字段设置节点的处理人范围？例如：某节点只能由 `nexlyn_org_id=org-001` 的用户处理

#### 关于 Webhook 通知
3. ❓ **Webhook 支持**：流程状态变更时，能否通过 webhook 通知外部系统（Nexlyn）？支持哪些事件类型（发起、审批、拒绝、完成等）？
4. ❓ **Webhook 数据**：Webhook 通知中会包含哪些信息？能否获取业务字段数据（如 `nexlyn_user_id`）？

#### 关于数据查询
5. ❓ **API 查询能力**：流程查询 API 能否支持复杂条件（按业务字段过滤、组织过滤、统计分析等）？
6. ❓ **只读数据库**：是否提供只读映射数据库访问权限？数据结构与主库一致吗？

## 附录：补充说明

### 关于手机端使用 Skylark 服务号（方案 1）

**原因**：
- Skylark 微信服务号已包含完整的流程处理功能
- 用户可以在微信中直接审批、评论、查看流程
- 无需跳转到外部页面

**用户体验**：
- **电脑端**：在 Nexlyn 网页平台操作（统一体验）
- **手机端**：在 Skylark 微信服务号操作（利用已有能力）

**优势**：
- 无需 Nexlyn 重复开发微信流程处理功能
- Skylark 微信功能已成熟稳定

**劣势**：
- 品牌不统一（微信端是 Skylark 品牌）
- 用户需要理解"电脑用 Nexlyn，手机用 Skylark 微信"

### 关于 Webhook 通知（方案 2）

**Skylark 支持的 Webhook**：
- 流程状态变更（发起、审批、拒绝、完成等）
- Skylark 调用 Nexlyn 提供的 Webhook 接口
- 传递流程实例 ID、当前状态、下一处理人等信息

**Nexlyn 接收 Webhook 后的处理**：
1. 解析流程状态
2. 查询下一处理人的 Nexlyn 用户 ID（从业务字段 `nexlyn_handler_id`）
3. 查询该用户的微信 openid
4. 调用微信 API 推送模板消息

**问题**：管理员误操作用户/组织无 Webhook
- Webhook 只覆盖流程相关事件
- 如果 Skylark 管理员手动修改用户/组织，没有通知机制
- 但方案 2 不涉及用户/组织同步，所以这不是问题
